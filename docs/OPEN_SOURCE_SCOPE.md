# 开源范围与发布边界（讨论稿）

## 1. 开源程度选项

| 方案 | 开源内容 | 优点 | 风险 |
|---|---|---|---|
| A 只开文档 | 架构/方法论 | 最简单 | 不可复现 |
| B 开核心代码（推荐） | 账本、Resolver、CaseEvaluator、compiler 接口、测试、合成数据 | 可复现、可审查、保留数据壁垒 | 需清理历史与数据 |
| C 开完整链路 | B + 真实 LLM/MCP/年报解析 | 影响大 | 版权/数据/运维风险高 |
| D 全私仓公开 | 完整内部生产仓 | 不推荐 | 业务数据、题库、内部资料不可控 |

## 2. 推荐：方案 B

开源：

- `fin_wiki/` 核心包；
- `tests/`（合成数据）；
- `docs/ARCHITECTURE.md`、`README.md`；
- `examples/` 脱敏示例；
- LICENSE、CONTRIBUTING、SECURITY。

保留闭源：

- 生产实现/内部题库/经验库；
- 真实年报/公告 PDF 与抽取结果；
- 题库原题、真题答案、内部部署配置；
- 任何业务资料与密钥。

## 3. 许可证

- 本仓库采用 **MIT**（更宽松；如后续需要专利授权可改 Apache-2.0）；
- 第三方依赖（pydantic 等）保持原许可证；
- 如引用外部参考实现，保留其原许可证与署名。

## 4. 发布前检查

1. 独立目录导出，不继承私仓历史；
2. 扫密钥/内部路径/业务名称；
3. 扫版权内容（题库/年报/教材）；
4. 从零跑测试；
5. README 写清定位、边界、快速开始；
6. 建 public repo，首个 tag `v0.1.0`。

## 5. 对外表述

- 定位：确定性财务计算 + 可追溯知识证据的 **参考实现**；
- 明确“不构成审计/法律意见”；
- 明确“LLM 只做抽取，不做计算/入账”；
- 案例评估只输出“疑似/需核”，不输出“违规”。
